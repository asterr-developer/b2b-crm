# B2B CRM

PHP, Laravel, Inertia, Vue 3, TypeScript, Tailwind CSS и PostgreSQL.

Демо показывает продажи корпоративного размещения от заявки до приёмки брони и отметки об оплате. При переносе на условиях новой версии КП исходная бронь сохраняется, если номера уже заняли. См. [сценарий показа](DEMO.md), [проверки релиза](RELEASE.md) и [исследование CRM](CRM-RESEARCH.md).

## Локальный запуск

Нужны PHP с расширением `pdo_pgsql`, Composer, Node.js и Docker Compose. Скопируйте `.env.example` в `.env` и задайте локальный пароль в `DB_PASSWORD`.

```sh
composer install
npm ci
docker compose -p b2b-crm up -d --wait
php artisan key:generate
php artisan migrate
npm run build
php artisan serve --port=8010
```

На Windows установите зависимости командой `composer install --ignore-platform-req=ext-pcntl --ignore-platform-req=ext-posix`. Эти два расширения нужны только воркеру Horizon, который запускается в Linux-контейнере.

Откройте [регистрацию](http://127.0.0.1:8010/register). После регистрации откроется воронка продаж. Создайте сделку, указав компанию и контакт, и проведите её через квалификацию и предложение. Для выигрыша сделки нужна положительная сумма.

## Командный доступ

Оператор с доступом к консоли может подключить зарегистрированных пользователей к отделу.

```sh
php artisan crm:team-member manager@example.com "Продажи" manager
php artisan crm:team-member lead@example.com "Продажи" lead
```

Менеджер видит свои сделки. Руководитель видит сделки отдела и может менять ответственного по сделкам и заявкам. В "Отделе продаж" руководитель создаёт одноразовую ссылку для менеджера и исключает менеджера после передачи записей. Команда консоли нужна для назначения руководителя и явного переноса личных записей сотрудника в отдел.

## Демобаза

Создайте отдельную PostgreSQL `crm_demo` и укажите локальный пароль для трёх синтетических учётных записей. Пример для PowerShell.

```powershell
docker compose -p b2b-crm exec -T postgres createdb -U crm crm_demo
$env:DB_DATABASE = 'crm_demo'
$env:CRM_DEMO_PASSWORD = '<пароль от 12 символов>'
$env:SESSION_COOKIE = 'crm_demo_session'
$env:APP_URL = 'http://127.0.0.1:8011'
php artisan migrate
php artisan db:seed --class=HospitalityDemoSeeder
php artisan serve --host=127.0.0.1 --port=8011
```

Вход под `manager@hotel.example.test`, `lead@hotel.example.test` или `lodging@hotel.example.test`. Новые демоаккаунты используют заданный пароль. Повторное заполнение сохраняет действующие пароли. Откройте [заявки демо](http://127.0.0.1:8011/group-requests). Для демонстрации сбоя очереди используйте отдельную базу по инструкции из сценария.

## Резервная копия

Снимок PostgreSQL делается через `pg_dump -Fc`. Проверьте его командой `pg_restore --list`, восстановите в отдельную пустую базу и сравните число компаний, контактов, сделок, предложений, задач и переходов. Сделайте это перед любой миграцией, которая меняет существующие связи. Дампы содержат данные CRM, поэтому не добавляйте их в репозиторий.

## Сделки, предложения и напоминания

Карточка открывается по названию сделки. В ней можно добавить контакты с ролями, заметки и задачи, указать плановую дату закрытия и причину проигрыша, посмотреть историю переходов и создать версию коммерческого предложения. Для согласования нужен руководитель отдела. После согласования скачайте PDF, отправьте его клиенту и отметьте отправку в CRM. Когда клиент ответит, отметьте ответ в карточке.

Руководитель задаёт названия этапов, обязательность даты и причины, а также число календарных дней до напоминания. Ноль отключает напоминания. Планировщик каждый час ставит в очередь проверку отправленных предложений. Если по актуальной версии ещё нет ответа и сделка остаётся на этапе предложения, CRM создаёт одну задачу на версию.

В "Воронках отдела" можно создать отдельную доску с дополнительными этапами квалификации и предложения. Руководитель переносит туда новую сделку. В отчётах дополнительные этапы сохраняют общую бизнес-категорию. Руководитель также может настроить задачу, которую CRM создаст при переходе в выбранную категорию.

В "Клиентах" руководитель проверяет и загружает CSV в UTF-8 с заголовком `company,contact,email`. Повторный импорт использует существующие записи. Объединение требует выбрать основную компанию и подтвердить перенос. Исходная карточка остаётся архивной, её адрес ведёт к основной.

## Интеграции

### ERP / учётная система

- `GET /api/erp/v1/bookings` возвращает подтверждённые брони отдела, категории, даты и плановые платежи. Запрос использует `Authorization: Bearer <CRM_ERP_READ_TOKEN>`. Передавайте `next_after` как `after` до получения `null`. Для сверки отмен начинайте новый проход без курсора. Имена гостей и контактные данные в выгрузку не входят.
- `POST /api/erp/v1/deals/{deal}/payments/{kind}` принимает подтверждение уже запланированного платежа. `kind` - `deposit` или `balance`. Пример JSON: `{"revision":1,"amount":"3000.00","currency":"RUB","reference":"ERP-17"}`. Передайте Unix-время в секундах через `X-CRM-Timestamp` и подпись HMAC-SHA256 в hex через `X-CRM-Signature`. Подпишите строку `timestamp.POST.path.raw_body` ключом `CRM_ERP_WRITE_SECRET`. `path` начинается с `/api/erp/v1/`. Повтор с тем же номером и суммой возвращает `applied: false`. Расхождение суммы, ревизии или номера уже полученного платежа возвращает HTTP 409.
- Укажите `CRM_ERP_DEPARTMENT_ID` и отдельные ключи длиной от 32 символов. Пока соответствующий ключ не задан, маршрут выключен. При внешнем размещении передавайте ключ и подпись через HTTPS.

- После согласования предложения доступен черновик письма `.eml` с адресом клиента и PDF. Отправку и ответ регистрирует сотрудник.
- Задачу со сроком можно выгрузить в календарь как `.ics`. Это событие на 15 минут со временем начала в UTC. [Формат iCalendar](https://www.rfc-editor.org/rfc/rfc5545.html)
- Чтобы подключить внешнюю форму, задайте `CRM_INTAKE_WEBHOOK_SECRET` длиной от 32 символов и почту ответственного менеджера отдела в `CRM_INTAKE_WEBHOOK_ASSIGNEE`. Без этих настроек маршрут выключен. Отправляйте JSON на `POST /api/intake/group-requests` с полями `title`, `company_id` или `company_name`, `contact_name`, `email` и необязательным `notes`.

Для вебхука передайте `Accept: application/json`, `Content-Type: application/json`, `X-CRM-Timestamp` в Unix-секундах, `X-CRM-Event` с уникальным ID события и `X-CRM-Signature` с HMAC-SHA256 в hex. Подпись считается по строке `timestamp.event.raw_body` с секретом интеграции. Повтор идентичного события возвращает исходный ID заявки. Для спорного клиента приложение возвращает ошибку валидации. Сотрудник выбирает нужную компанию, после чего отправитель может повторить приём с `company_id` и новой подписью.

```sh
docker compose -p b2b-crm --profile automation up -d --build
docker compose -p b2b-crm exec horizon php artisan horizon:status
```

Отчёты доступны из воронки и учитывают права пользователя. Прогноз берёт открытые сделки с плановой датой и применяет вероятность 10%, 35% или 70% в зависимости от этапа.

Срез взвешенного прогноза сохраняется раз в сутки в 00:15 по часовому поясу приложения. За дату сохраняется первый успешный срез. Для проверки вручную запустите `php artisan crm:capture-forecast` на демобазе.

## Размещение и отправка предложений

Календарь показывает фонд, занятость и свободные номера для каждой ночи выбранной категории. В сводке указана ночь с минимальной доступностью. Руководитель может изменить фонд на одну дату, например установить ноль для обслуживания, или вернуть базовое значение. Изменение с причиной сохраняется в журнале. Действующие брони и резервы ограничивают уменьшение фонда.

1. Войдите руководителем и откройте "Размещение". Добавьте категорию с одним номером или используйте демокатегорию "Последний номер". Руководитель задаёт срок резерва по умолчанию и создание задачи для службы размещения.
2. Войдите менеджером и квалифицируйте две заявки с пересекающимися датами. Создайте резерв на одну из них. Вторая получит сообщение о нехватке номера. День выезда освобождает номер для следующего заезда. Просроченный резерв перестаёт занимать номер сразу, а `php artisan crm:expire-reserves` переносит его в историю.
3. Конвертируйте заявку, создайте предложение, согласуйте его под руководителем и зафиксируйте отправку, ответ и согласие клиента. Подтвердите резерв всех категорий одной операцией. Для переноса нажмите "Подготовить перенос", укажите новые даты, состав и итоговую цену. CRM проверит доступность и создаст отдельную версию КП. После согласования и явного согласия клиента нажмите "Подтвердить перенос" в карточке сделки. CRM повторно проверит фонд, заменит бронь и обновит сумму сделки одной транзакцией. Если фонд успел закончиться, исходная бронь и её сумма сохранятся. Старые версии КП остаются в истории. Для подготовки переноса и отмены обязательна причина. Эти операции доступны до дня заезда включительно.
4. Для почтовой отправки включите `CRM_PROPOSAL_EMAIL=true` и настройте почтовый транспорт приложения. Для демонстрации используйте изолированную почту с синтетическим адресом. Нажатие по согласованной версии ставит PDF в очередь. Планировщик обрабатывает её раз в минуту, вручную доступна команда `php artisan crm:deliver-proposals`. Статус "Принято почтовым транспортом" означает передачу письма транспорту. При разрыве во время отправки сверяйте результат с почтовым журналом перед явным повтором, чтобы избежать копий. История доступна руководителю в разделе "Размещение".
5. В форме уточнения заявки вставьте, например, "Заезд 2028-05-12, выезд 2028-05-14, 24 гостя". Проверьте подсказку и цитату, подставьте значения и подтвердите форму. Парсер работает локально. При наличии Ollama на машине, где работает PHP, установите `CRM_OLLAMA_MODEL` в имя установленной модели. В этом режиме PHP по кнопке передаёт текст локальному Ollama на порту 11434. При недоступности модели остаётся базовый разбор. Пожелания отображаются для проверки. [Ollama Chat API](https://docs.ollama.com/api/chat)

Тест `HospitalityTest` воспроизводит исключение с последним номером, освобождение после истечения и восстановление незавершённой отправки с одним PDF в тестовом транспорте. Для проверки настоящего параллельного доступа создайте пустую PostgreSQL `inventory_crm_demo`, назначьте её через `DB_DATABASE`, задайте `CRM_DEMO_PASSWORD` и выполните `php artisan migrate --seed --seeder=HospitalityDemoSeeder`, затем `php scripts/verify-last-room.php`. Скрипт удерживает блокировку до прихода двух независимых сессий и проверяет, что только одна создаёт резерв.

## Входящие ответы и узкие места

Полученное письмо останавливает напоминание, но согласие клиента фиксируется отдельно в карточке актуального КП. Доступны согласие, отказ, запрос изменений и разбор. При запросе изменений CRM создаёт задачу. Для закрытия групповой сделки как выигранной нужны согласие и бронь по этой версии. Прежние ответы без указанного решения требуют ручной проверки. Для открытой сделки с прежней бронью подтвердите решение в карточке КП, затем нажмите "Связать бронь с принятым КП" в разделе размещения.

- Для проверки без почтового провайдера руководитель регистрирует синтетическое письмо в разделе "Входящие" и выбирает сделку и версию отправленного КП. Менеджер видит связанные письма своих сделок. При привязке ответ появляется в карточке сделки и закрывает напоминание по этой версии.
- Для автоматического приёма настройте `CRM_REPLY_WEBHOOK_SECRET` (от 32 символов) и `CRM_REPLY_WEBHOOK_ACCOUNT` (почта сотрудника целевого отдела). Внешний адаптер авторизованного почтового ящика передаёт JSON на `POST /api/intake/replies` с полями `sender`, `subject`, `body` и `in_reply_to`. Правило подписи и заголовки совпадают с вебхуком заявок. Для автоматической привязки адаптер должен сохранить оригинальный `In-Reply-To`, а адрес отправителя должен совпасть с получателем КП. Сохраняйте уникальный ID письма в `X-CRM-Event`. Если совпадение спорное, письмо попадёт на ручную проверку руководителю. Чтение почтового ящика и проверка подлинности отправителя выполняются на стороне адаптера.
- В "Отчётах по продажам" откройте "Узкие места процесса". Время до первого КП считается от создания сделки до первой зарегистрированной отправки. Время согласования считается от регистрации первой версии до первого одобрения. Время до ответа считается от отправки той версии КП, к которой привязано первое входящее письмо. В среднее входят сделки с обеими отметками времени. Просрочки и причины проигрыша доступны с переходом к исходной сделке.

## Синхронизация общего почтового ящика

Адаптер `scripts/sync-mailbox.py` читает общий ящик по IMAP с проверкой TLS и передаёт письма существующему вебхуку. Нужен Python 3.10 или новее. Адаптер открывает папку на чтение и не меняет флаги писем. CRM получает только текстовую часть. HTML и вложения остаются в исходном ящике. Время во "Входящих" означает время поступления в CRM.

- Задайте `CRM_REPLY_WEBHOOK_ACCOUNT` в окружении Laravel и передайте одинаковый `CRM_REPLY_WEBHOOK_SECRET` с обеих сторон.
- В окружении адаптера задайте `CRM_IMAP_HOST`, `CRM_IMAP_USER`, `CRM_IMAP_PASSWORD`, `CRM_IMAP_STATE` (путь к файлу SQLite с контрольной точкой) и `CRM_MAILBOX_ENDPOINT` (HTTPS-адрес `/api/intake/replies` либо локальный URL). Порт по умолчанию 993, папка `INBOX`. Для них доступны `CRM_IMAP_PORT` и `CRM_IMAP_FOLDER`. Подходит провайдер с IMAP-входом по паролю приложения. Ящики, требующие OAuth, этой версией не поддерживаются.
- По умолчанию ответы проходят ручную проверку. Включайте автопривязку через `CRM_IMAP_TRUSTED_AUTHSERV_ID` только для сервера, который удаляет поддельные заголовки от своего имени на границе и сам добавляет результат DMARC. Для привязки также нужны совпадающий отправитель и оригинальный `In-Reply-To`. Автоответы, сообщения о недоставке и письма без текстовой части остаются на проверке.
- Запуск `python scripts/sync-mailbox.py` читает до 25 сообщений. Первый запуск начинает отслеживать новые письма. Для импорта уже имеющихся используйте `--import-existing` при первом запуске с новым файлом состояния. Для регулярной работы запускайте один экземпляр каждую минуту и отслеживайте код возврата. После сбоя повторите запуск с тем же файлом. Контрольная точка продвигается после подтверждения CRM. Письма больше 2 МиБ пропускаются с записью UID в журнале.

Тесты адаптера запускаются командой `python -B scripts/test-sync-mailbox.py`. Они проверяют формат подписи на локальном HTTP-сервере, повтор после потери ответа, смену UIDVALIDITY и условия автопривязки.

Руководитель видит во "Входящих" последний запуск адаптера, последний успешный запуск и счётчики последнего цикла. Если адаптер перестал передавать статус, после трёх минут при открытии или обновлении страницы появится предупреждение.

## Приёмка службой размещения

В действующей брони доступен "Список гостей". Загрузите CSV в UTF-8 или вставьте его текст с заголовком `name,allocation,room`. Номера позиций и диапазоны комнат указаны в карточке. Предпросмотр проверяет, что позиция принадлежит брони, номер комнаты входит в выделенный диапазон и общее число гостей не превышено. Частичный список можно сохранить и дополнить новой версией. Повтор того же импорта не создаёт дубликат. После переноса прежние номера позиций не применяются к новой брони. В истории сделки сохраняются автор, версия и число записей без имён гостей.

Зарегистрированному сотруднику можно назначить роль `lodging` командой `php artisan crm:team-member <email> "<название отдела>" lodging`. Сотрудник увидит действующие брони своего отдела. Он может принять бронь или вернуть её с причиной. Возврат создаёт или переоткрывает задачу продаж. После переноса новая бронь проходит приёмку заново. Руководитель также может принять решение. Событие и причина видны в карточке сделки.

## Депозит и оплата

В карточке сделки можно запланировать депозит и остаток в рублях. Общая сумма плана ограничена суммой сделки. Срок заканчивается в 23:59 по московскому времени, после него незакрытая задача попадает в просрочку. После подтверждения поступления задача закрывается. Учёт ручной, без перевода денег и банковской сверки.

Синтетическая заявка "Деловая делегация · сентябрь 2026" использует даты 22-25.09.2026. Для демонстрации нового резерва используются отдельные заявки с ещё не наступившим заездом.

## Проверки

"Моя работа" доступна по адресу `/work`. Менеджер видит свои записи, руководитель видит отдел и задаёт срок первого ответа от 1 до 168 календарных часов. По умолчанию действует 24 часа. Текущее правило применяется ко всей выборке. Срок отсчитывается от приёма заявки. После содержательного контакта сотрудник фиксирует канал и краткий итог. Статистика за 30 дней показывает медиану и 90-й перцентиль по зафиксированным ответам. Отдельно показаны просроченные открытые заявки и поздние ответы.

## Интеграция со "Сметой"

Настройте в CRM CRM_ESTIMATE_URL (базовый адрес "Сметы"), CRM_ESTIMATE_TOKEN (отдельный случайный секрет от 32 символов), CRM_ESTIMATE_SOURCE (стабильный идентификатор CRM из строчных латинских букв, цифр и дефисов) и CRM_ESTIMATE_DEPARTMENT_ID (ID отдела, которому разрешён обмен). В рабочем окружении используйте HTTPS.

В "Смете" примените миграции, задайте тот же секрет в ESTIMATE_CRM_TOKEN и ID выделенного владельца черновиков в ESTIMATE_CRM_OWNER_ID. В карточке сделки создайте черновик и откройте его в кабинете этого владельца. Заполните позиции, выпустите смету и примите её по клиентской ссылке. После обновления карточки CRM покажет номер, сумму в рублях и ссылку на принятую версию. Сумма самой сделки не меняется.
